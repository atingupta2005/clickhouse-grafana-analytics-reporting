# Session 16 — Kafka Concepts and Kafka Jobs

## Core Lab

### Lab Objective

In this lab, follow an order event from an application through Kafka and into ClickHouse.

The lab is an **architecture walkthrough**, not a Kafka administration exercise. You do not need to produce or consume real Kafka messages.

---

Start with the reporting architecture used in this course:

```text

 v
```

### Expected Result

You should be able to identify:

- Kafka as the event/data-movement layer
- ClickHouse as the analytics store
- Grafana as the reporting and visualization layer

### Tip

Remember that Grafana continues to query ClickHouse. Kafka is upstream of the reporting layer.

The diagram is a **typical architecture**. The shared training seed in `training.v_lab_orders` is already loaded for class — this session does **not** claim Kafka currently populates that view.

## 2. Examine a Sample JSON Order Event

Consider this example event:

```json
{
 "event_type": "order_completed",
 "order_id": 10001,
 "customer_id": 501,
 "region_id": 3,
 "order_date": "2025-06-18",
 "sales_amount": 2450.50
}
```

Discuss the role of each field.

| Field | Purpose |
|---|---|
| `event_type` | Identifies what happened |
| `order_id` | Identifies the order |
| `customer_id` | Identifies the customer |
| `region_id` | Identifies the region |
| `order_date` | Business date |
| `sales_amount` | Order value |

### Expected Result

You should be able to explain why an event needs a business identifier and the information required by its downstream consumers.

### Tip

The JSON above is a **teaching example**, not a statement that this exact payload is generated by the lab application.

## 3. Trace the Event to a Kafka Topic

Assume the application publishes the event to:

```text
orders
```

The conceptual flow is:

```text
Order Application
 |
 | JSON event
 v
 orders topic
```

Answer these questions:

1. What is the producer?
2. What is the topic?
3. What information is contained in the message?
4. Why does the application not need to know which reporting application will consume the event?

### Expected Result

You should identify:

- **Producer:** order application
- **Topic:** `orders`
- **Message:** JSON order event
- **Decoupling:** consumers can independently process the event

## 4. Add Partitions

Assume the `orders` topic has three partitions:

```text
orders
 |
 +-- Partition 0
 +-- Partition 1
 +-- Partition 2
```

Discuss the following scenario:

```text
Order 10001
Order 10002
Order 10003
Order 10004
```

If `order_id` is selected as the partition key, related events for the same order can be routed consistently to a partition.

### Expected Result

You should be able to explain:

- Why partitions are used
- How partitions provide parallelism
- Why the partition key can matter
- That ordering is maintained within a partition

### Tip

Remember: Kafka does not provides one global ordering across all partitions.

## 5. Add Consumers and a Consumer Group

Now extend the architecture:

```text
 orders
 / | \
 / | \
 v v v
 Partition 0 1 2
 | | |
 v v v
 C1 C2 C3
 \ | /
 \ | /
 Consumer Group
```

Discuss:

- Why multiple consumers can process partitions in parallel
- Why a consumer group is used
- What happens when there are more consumers than available partitions
- Why a second consumer group can independently consume the same topic

### Expected Result

You should understand that consumer groups provide coordinated processing and scaling.

## 7. Understand a Kafka Job

Consider this conceptual processing job:

```text
Kafka
 |
 v
Order Processing Job
 |
 +--> Validate event
 |
 +--> Transform data
 |
 +--> Filter invalid events
 |
 +--> Enrich data
 |
 v
ClickHouse
```

Discuss what should happen if an event is invalid.

Possible design approaches include:

- Reject the event
- Retry processing
- Send the event to an error-handling path
- Record the failure for investigation

### Expected Result

You should be able to identify processing responsibilities separately from Kafka's role as the event-streaming platform.

## 8. Compare Streaming and Batch

Compare these two designs.

### Design A — Streaming

```text
Application
 |
 v
 Kafka
 |
 v
Processing
 |
 v
ClickHouse
```

### Design B — Batch

```text
Database
 |
 v
Scheduled ETL
 |
 v
ClickHouse
```

Discuss:

1. Which design is appropriate when data must be processed continuously?
2. Which design may be simpler for daily reporting?
3. What requirement would justify adding Kafka?

### Expected Result

The decision should be based on requirements such as freshness, event volume, multiple consumers, decoupling and continuous processing—not simply on the availability of Kafka.
